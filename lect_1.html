Основні поняття та термінологія

Якість ПЗ (ISO/IEC 25010)

Ступінь відповідності програмної системи встановленим та неявним потребам зацікавлених сторін під час експлуатації в заданих умовах.

Надійність ПЗ

Ймовірність безвідмовної роботи програми протягом заданого проміжку часу. Включає відмовостійкість та відновлюваність.

Ланцюжок виникнення проблем (ISTQB / IEEE)

Error (Помилка людини) ➔ Defect (Дефект у коді) ➔ Failure (Відмова системи)

Приклад з e-commerce:

  • Error: Втомлений розробник забув додати перевірку на від'ємне значення ціни.
  • Defect: У коді відсутня логіка if (price < 0) throw Error;. Баг «спить» у системі.
  • Failure: Користувач вводить -100 грн, система падає під час спроби провести транзакцію.

Класифікація метрик якості

За об'єктом вимірювання

  • Метрики продукту — характеристики коду (складність, розмір)
  • Метрики процесу — ефективність розробки (швидкість, DORA metrics)
  • Метрики проєкту — управлінські показники (бюджет, термін)

За способом отримання

  • Прямі метрики — безпосереднє вимірювання (LOC, кількість дефектів)
  • Непрямі метрики — розраховані показники (щільність дефектів, складність McCabe)

Основні групи метрик:

📏 Метрики розміру LOC, SLOC, Function Points

🔗 Метрики структури Coupling (зв'язаність), Cohesion
⚡ Метрики надійності MTTF, MTBF, Availability

Граф потоку керування (Control Flow Graph)

CFG — це візуальне представлення всіх можливих маршрутів виконання програми. Він є основою для точного математичного розрахунку цикломатичної складності.

1. Вихідний код та Граф

function checkNumber(a) {
  // [1]
  if (a > 0) { 
      return "Pos"; // [2]
  } else {
      return "Neg"; // [3]
  }
  // [4] Exit
}

2. Аналіз та розрахунок

  • Вузли (N) = 4
    (Блоки коду, що виконуються послідовно)
  • Ребра (E) = 4
    (Стрілки переходів між вузлами)

Фундаментальна формула:

V(G) = E - N + 2P

V(G) = 4 - 4 + 2(1) = 2

*P = 1, оскільки ми аналізуємо одну цілісну функцію

Перевірка спрощеною формулою:
1 предикат (if) + 1 = 2.
Результати абсолютно збігаються!

Цикломатична складність (McCabe, 1976)

Визначення

Вимірює кількість лінійно незалежних шляхів виконання коду. Прямо вказує на мінімальну кількість Unit-тестів для 100% покриття гілок.

Формула:

V(G) = π + 1

де π — кількість предикатів (точок розгалуження: if, for, while, case, &&, ||, ?:)

Приклад підрахунку:

function check(a, b) {
  if (a > 0) {       // +1
    while (b > 0) {  // +1
      b--;
    }
  }
} // V(G) = 2 + 1 = 3

Інтерпретація значень:

Значення V(G) Оцінка складності Рішення (Рефакторинг)
1 - 10 Простий лінійний код Норма
11 - 20 Помірна складність Потребує уваги
21 - 50 Складний код Обов'язковий рефакторинг

Архітектурні метрики (Coupling & Cohesion)

Зв'язаність (Coupling) ⬇️ Мінімізуємо

Взаємозалежність між різними модулями.

  • Погано (Content Coupling): Модуль А безпосередньо змінює приватну змінну Модуля Б (напр. через Reflection).
  • Середньо (Control Coupling): Передача boolean-прапорців, що змінюють логіку іншого модуля.
  • Добре (Data Coupling): Передача лише необхідних примітивних даних (напр. calc(int a, int b)).

Зчеплення (Cohesion) ⬆️ Максимізуємо

Спорідненість функцій всередині одного модуля.

  • Погано (Логічне): Utils.processEverything() — звалено все підряд.
  • Середньо (Часове): Функції згруповані лише тому, що виконуються разом (напр. initDBAndLoadConfig()).
  • Добре (Функціональне): Math.calculateTax() — виконує строго одну чітку задачу (відповідає SRP).

🎯 Золоте правило архітектури

Низька зв'язаність (Low Coupling) + Високе зчеплення (High Cohesion)

Метрики надійності ПЗ

Щільність дефектів (DD)
DD = Кількість дефектів / KLOC

Типові значення: 1-25 дефектів на тисячу рядків коду.

MTTF (Mean Time To Failure)
MTTF = Загальний час / Кількість відмов

Середній час безперебійної роботи (як довго система живе до падіння).

MTBF (Mean Time Between Failures)
MTBF = MTTF + MTTR

MTTR — середній час відновлення (ремонту) після інциденту.

Коефіцієнт готовності (Availability)
A = MTTF / (MTTF + MTTR) × 100%

Частка часу, коли система доступна (напр., "Три дев'ятки" = 99.9%).

Метрики тестового покриття (Coverage)

Statement Coverage (Покриття інструкцій)

Відсоток рядків коду, що були виконані хоча б раз під час тестів. Найслабша метрика.

Branch Coverage (Покриття гілок)

Перевіряє обидва результати (True та False) для кожної умови if/else. Стандарт для Enterprise CI/CD (мінімум 80%).

Приклад: Condition Coverage (Покриття умов)

Маємо код: if (user.isActive && user.hasBalance) { ... }

Щоб досягти 100% Condition Coverage, недостатньо протестувати загальний `true` і `false`. Необхідно протестувати комбінації кожного операнда:

  • ✅ true && true
  • ✅ true && false
  • ✅ false && true
  • ✅ false && false

Технічний борг (Technical Debt)

Визначення: Накопичена вартість відкладених завдань з рефакторингу або виправлення субоптимальних (але тимчасово працюючих) рішень.

⚠️ Як виникає борг? (Приклад)

Розробник ігнорує попередження SonarQube про дублювання коду, щоб встигнути до релізу в п'ятницю. Код працює, але через місяць зміна бізнес-логіки вимагає правити код у 5 різних місцях. В одному місці забувають — стається критичний баг.

Фінансовий показник:

TDR = Вартість виправлення / Вартість розробки

Критичний поріг (Quality Gate): ≤ 5%

✓ Стратегії виплати

  • Жорсткі правила Linter.
  • Обов'язкове Code Review.
  • Виділення 20% ємності спринту на тех. таски.

5
Оптимізований (Optimizing)

Безперервне інноваційне вдосконалення та R&D. Адаптація до змін ринку.

Практика: Розрахунок метрик (До рефакторингу)

1. Цикломатична складність McCabe

Рахуємо предикати (умови):

  1. if (price > 0)
  2. if (type === 'student')
  3. else if (type === 'veteran')
  4. else if (isMember)
  5. if (price > 1000)
V(G) = 5 + 1 = 6

2. Лексичні метрики Halstead

  • Унікальні оператори (n1): 10 (if, else, ===, >, *=, return, {}, (), ,, function)
  • Унікальні операнди (n2): 11 (price, type, isMember, 'student', 0.9...)
Словник (n) = 10 + 11 = 21
Довжина (N) = 25 + 20 = 45
Зусилля (Effort, E) ≈ 1796

Практика: Рефакторинг коду

Застосовуємо патерни Early Return (Раннє повернення), Dictionary (Словник) та виносимо логіку калькуляції в окрему функцію (SRP). 

function applyDiscount(price, rate) { 
    return price * rate; 
}

function calculateDiscount(price, type, isMember) {
    if (price <= 0) return price;
    
    const discounts = { student: 0.9, veteran: 0.85 };
    if (discounts[type]) {
        return applyDiscount(price, discounts[type]);
    }
    
    if (isMember) {
        return applyDiscount(price, price > 1000 ? 0.8 : 0.9);
    }
    
    return price;
}

Практика: Розрахунок метрик (Після рефакторингу)

1. Цикломатична складність McCabe

Рахуємо предикати у calculateDiscount:

  1. if (price <= 0)
  2. if (discounts[type])
  3. if (isMember)
  4. price > 1000 ? ... : ... (Тернарний оператор = розгалуження)
V(G) = 4 + 1 = 5

2. Лексичні метрики Halstead

  • Унікальні оператори (n1): 13 (додався const, об'єкт {}, масив [])
  • Унікальні операнди (n2): 13 (додався applyDiscount, discounts)
Словник (n) = 13 + 13 = 26
Довжина (N) = 24 + 23 = 47
Зусилля (Effort, E) ≈ 2540

Висновки

🎯 Ключові положення

1. Еволюція до багатовимірності

Сучасний стандарт ISO/IEC 25010:2023 об'єднує 9 характеристик, акцентуючи увагу на кібербезпеці, гнучкості та безпечності.

2. Кількісне вимірювання (Метрики)

Архітектурна якість — це не суб'єктивна оцінка. Цикломатична складність, покриття тестами та LCOM дають чіткі індикатори технічного боргу.

3. Золоте правило модульності

Системи повинні проєктуватися за принципом: High Cohesion (високе зчеплення всередині) та Low Coupling (низька взаємозалежність).

4. Процесна зрілість та CI/CD

Високий рівень за CMMI досягається інтеграцією інструментів SAST/SCA/Coverage у пайплайни з жорсткими Quality Gates.
